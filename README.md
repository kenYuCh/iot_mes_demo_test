# IoT Smart Factory · Serverpod × Flutter

An IoT management project built with a Flutter app and a Serverpod backend, featuring site and device management, real-time monitoring, production workflows, alarms, device pairing, and OTA firmware updates.

> This guide covers local development. Screenshots show an existing environment; a new database will not automatically contain the devices or data shown here.

## Project Structure

```text
pod_app_v1/
├── pod_app_v1_flutter/   # Flutter app, Riverpod state management, and UI
├── pod_app_v1_server/    # Serverpod API, MQTT, data models, and migrations
├── pod_app_v1_client/    # Generated Serverpod Dart client
├── screenshot/          # App screenshots
├── pubspec.yaml         # Dart / Flutter workspace
└── AGENTS.md            # Development guidelines
```

The main modules cover sites and devices, telemetry, device control, operations, production and OEE, alarms, access sharing, BLE pairing, and OTA updates. The app receives data through the Serverpod API and Streaming. Devices connect to Mosquitto over MQTTS, while the backend handles incoming device data and control commands.

```text
Flutter App ↔ Serverpod API / Streaming ↔ PostgreSQL / Redis
                         ↕
                  Mosquitto MQTTS
                         ↕
                     IoT Devices
```

## Development Environment

| Tool | Project Configuration |
| --- | --- |
| Flutter / Dart | Flutter `^3.32.0`, Dart `^3.8.0`; use an SDK compatible with the current dependencies |
| Serverpod / CLI | `3.4.11` |
| PostgreSQL | `pgvector/pgvector:pg16` |
| Redis | Compose currently uses `redis:7.2-alpine` |
| MQTT Broker | `eclipse-mosquitto:2`, mTLS, port `8883` |
| Other requirements | Docker Compose and OpenSSL; iOS also requires macOS, Xcode, and CocoaPods |

The commands below assume you start at the project root. In each terminal, switch to the indicated directory before running commands.

### 1. Install Dependencies and the CLI

```bash
# Project root: resolve dependencies for all three workspace packages
flutter pub get
dart pub global activate serverpod_cli 3.4.11
export PATH="$PATH:$HOME/.pub-cache/bin"
serverpod --version
```

### 2. Configure Passwords and Secrets

Create `pod_app_v1_server/config/passwords.yaml` locally and keep it out of version control. Following the Serverpod 3.4.11 configuration format, populate the `development:` section with:

| Key | Purpose / Configuration |
| --- | --- |
| `database` | Must match the PostgreSQL password in Compose |
| `redis` | Must match Redis `--requirepass` in Compose; update the healthcheck as well if changed |
| `serviceSecret` | Serverpod service secret; generate a separate random value |
| `jwtHmacSha512PrivateKey` | JWT signing secret; generate a separate random value |
| `jwtRefreshTokenHashPepper` | Refresh token hashing secret; generate a separate random value |
| `emailSecretHashPepper` | Email authentication secret; generate a separate random value |

Use `openssl rand -base64 64` to generate each random value separately. For integration tests, also configure a `test:` section with database and Redis passwords matching the test services in Compose. Use separate configuration and secrets for production.

Generate and configure certificates, private keys, and passwords locally. This README provides setup instructions without including actual key files.

### 3. Create the CA and Service Certificates

The database configuration already enables TLS. Create the Root CA first, then generate database and MQTT certificates before starting the containers. The current backend startup flow does not call `CaService.ensureCa`, so simply starting the server will not create a CA in a clean environment.

The following commands create a local CA using the filenames and certificate hierarchy expected by `CaService`. **Skip this block if a CA already exists to avoid overwriting the existing trust chain.**

```bash
cd pod_app_v1_server
mkdir -p certs/ca
openssl ecparam -name prime256v1 -genkey -noout -out certs/ca/root-ca.key
openssl req -x509 -new -key certs/ca/root-ca.key -sha256 -days 3650 \
  -subj "/C=TW/O=IoT Smart Factory/CN=IoT Root CA" \
  -addext "basicConstraints=critical,CA:TRUE,pathlen:1" \
  -addext "keyUsage=critical,keyCertSign,cRLSign" -out certs/ca/root-ca.crt
openssl ecparam -name prime256v1 -genkey -noout -out certs/ca/intermediate.key
openssl req -new -key certs/ca/intermediate.key \
  -subj "/C=TW/O=IoT Smart Factory/CN=IoT Device Intermediate CA" \
  -out certs/ca/intermediate.csr
printf 'basicConstraints=critical,CA:TRUE,pathlen:0\nkeyUsage=critical,keyCertSign,cRLSign\n' > certs/ca/intermediate.ext
openssl x509 -req -in certs/ca/intermediate.csr -sha256 \
  -CA certs/ca/root-ca.crt -CAkey certs/ca/root-ca.key -CAcreateserial \
  -days 1825 -extfile certs/ca/intermediate.ext -out certs/ca/intermediate.crt
chmod 600 certs/ca/*.key
```

Next, generate the service certificates from `pod_app_v1_server/`:

```bash
bash tool/setup_db_ssl.sh
bash tool/setup_mqtts.sh
```

When physical devices connect through a LAN IP, replace the second command with `MQTT_LAN_IP=192.168.1.100 bash tool/setup_mqtts.sh`, substituting your development machine's IP. This adds the IP to the broker certificate. These scripts regenerate the relevant service certificates and do not need to run during normal daily startup.

### 4. Start the Database, MQTT Broker, and Backend

```bash
# pod_app_v1_server/
docker compose up -d postgres redis mosquitto
docker compose ps
serverpod generate
```

Review the SQL in `migrations/` before applying migrations for the first time. Back up any existing database, then start the backend:

```bash
dart run bin/main.dart --apply-migrations
```

For physical devices, start the backend as follows so the pairing API returns a broker address the devices can reach:

```bash
MQTT_PUBLIC_HOST=192.168.1.100 dart run bin/main.dart --apply-migrations
```

`MQTT_HOST` is the address the backend uses to reach the broker (default: `localhost`). `MQTT_PUBLIC_HOST` is the address returned to devices.

| Service | Local Port |
| --- | --- |
| Serverpod API | `8080` |
| Serverpod Insights | `8081` |
| Web / Firmware Downloads | `8082` |
| PostgreSQL / Redis (TLS) | `8090` / `8091` |
| Mosquitto (mTLS) | `8883` |

### 5. Run the Flutter App

Open another terminal:

```bash
cd pod_app_v1_flutter
flutter devices
flutter run -d <device-id> --dart-define=AUTO_LOGIN=false \
  --dart-define=SERVER_URL=http://localhost:8080/
```

Replace `<device-id>` with an ID listed by `flutter devices`. The iOS Simulator can use `localhost`; the Android Emulator typically uses `http://10.0.2.2:8080/`. For a physical phone, use your development machine's LAN IP, for example:

```bash
flutter run -d <device-id> --dart-define=AUTO_LOGIN=false \
  --dart-define=SERVER_URL=http://192.168.1.100:8080/
```

The phone and development machine must be on networks that can reach each other, with the required service ports accessible. For a physical iOS device, also configure the Signing Team in Xcode. BLE pairing requires a physical phone and device.

### 6. Sign In and Prepare Initial Data

- During registration, development verification codes are printed in the backend terminal. A production email service is not yet connected.
- The commands above disable debug auto-login to avoid repeated attempts with a default test account that does not exist in a clean database.
- The server does not automatically run demo seeding or telemetry simulators. An administrator must import or create the Company, user Membership records, roles, and site data. Registering an account does not create a company.
- If no company exists, the API reports that no company data has been created. If a company exists but a new account has no Membership, the current logic adds the account to the first company with the viewer role. An administrator must assign appropriate roles for management operations.
- There is currently no one-command initializer for the first company and administrator. Prepare this data according to the models in `lib/src/company/` before using the full application in a clean environment.
- Real devices require factory records and Claim Codes, pairing, certificate issuance, and MQTT uplink traffic before actual measurements are available. The data shown in the screenshots is not loaded automatically with the app.

After completing the initial setup:

```bash
# Terminal A: pod_app_v1_server/
```

## Development and Checks

After changing a model (`.spy.yaml`) or an endpoint's public interface, run `serverpod generate` from the backend directory. Do not manually edit `lib/src/generated/` or the generated client. For database schema changes, run `serverpod create-migration --tag "feature-name"`, review the SQL, and then apply the migration.

```bash
# pod_app_v1_server/
dart format .
dart analyze
# Integration tests require test services, certificates, and the test section in passwords.yaml
docker compose up -d postgres_test redis_test
dart test

# pod_app_v1_flutter/
flutter analyze
flutter test
```

## Troubleshooting

| Issue | What to Check |
| --- | --- |
| `serverpod` command not found | Confirm the CLI is installed and `$HOME/.pub-cache/bin` is in PATH |
| Redis / PostgreSQL TLS failure | Create the CA before running `setup_db_ssl.sh`; check certificate mounts and matching passwords |
| MQTT does not connect | Check the output of `setup_mqtts.sh`, broker logs, and the IP in the certificate |
| Phone cannot reach the API | Use the development machine's LAN IP on physical devices; check `SERVER_URL` and network connectivity |
| No data or insufficient permissions after login | Confirm that Company, Membership, roles, and device data have been prepared |
| Images do not appear on GitHub | Commit and push `screenshot/`, preserving the exact paths and filename capitalization |

See [AGENTS.md](AGENTS.md) for development guidelines. This guide reflects the current code and Compose configuration. Local HTTP, terminal verification codes, and the initial tenant membership flow require separate configuration before production deployment.

## Permission Management

Permission management is temporarily provided through the app's management page, which is visible only to accounts with the relevant permissions. Permissions should ultimately be managed through a dedicated administration backend; designing that backend is outside the current scope.
